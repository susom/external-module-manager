RMA Charges Migration Plan

Move EM billing operations from R2P2 to REDCap External Module Manager with approval queue, PTA tracking, monthly billing export/import, and carry-forward logic.

Date: June 29, 2026 | Scope: New REDCap-only workflow (no legacy migration required)

1) Agreed Decisions

Confirmed Implementation Baseline

  • Approval should auto-enable requested EM(s) on approve.
  • A request can include multiple EMs.
  • Billing cutoff is end-of-month day 28/29.
  • Rejected charges carry forward next month with the same amount.
  • Finance upload should support all line statuses.
  • Request submission should be limited to project admins.
  • PTA changes affect future runs only (not already-generated lines).
  • No migration of historical R2P2 data is required.

2) Target Workflow (Recommended)

Sequential Queue Model

  1. Project admin opens request page and submits PTA + selected EMs.
  2. Request appears in super-user approval queue with per-EM line items.
  3. Super user approves/rejects each line (or bulk action).
  4. Approved lines auto-enable EM in REDCap project.
  5. Monthly billing run creates charge lines from approved + enabled + fee-bearing EMs at cutoff.
  6. Finance exports CSV, processes externally, re-uploads statuses.
  7. Rejected lines are recreated for the next month as carry-forward attempts.

3) Delivery Plan

Phase A - Request + Approval Build project-admin request page, super-user queue, and auto-enable action.
Phase B - Billing Engine Add monthly billing run creation, grouping by PTA and by Project views, and fee snapshot logic.
Phase C - Finance CSV Loop Export CSV template, import processed CSV, status updates, and carry-forward generation.
Phase D - Hard Cutover Turn on REDCap workflow as source of truth for all new billing periods.

Note: This plan intentionally excludes historical backfill from R2P2.

4) Data/Reporting Shape

  • Request Header: project, requester, PTA, status, timestamps.
  • Request Items: module prefix, fee snapshot, item status, approver info.
  • Billing Run: month/year, cutoff timestamp, run status.
  • Billing Lines: project, module, PTA, amount, status, attempt number, prior line link.
  • Views Needed: grouped by PTA and grouped by Project.
Billing Status Meaning Next Behavior
charged Finance completed charge Closed; no carry-forward
rejected Charge failed/rejected Create new line next month, same amount
waived Charge forgiven Closed; no carry-forward
hold Temporary hold by finance Remains open for policy decision
pending Awaiting finance result Await import update

5) Open Questions (Decision Checklist)

Needs Decision

  1. Approval granularity: Should super users approve per-request only, per-line only, or both?
  2. Reject behavior: If one line in a multi-EM request is rejected, should approved lines still auto-enable immediately?
  3. Cutoff timezone: Which timezone governs day 28/29 cutoff (server timezone, institution timezone, configurable)?
  4. Finance import key: What unique line identifier will finance preserve and return in CSV (line ID, external key, both)?
  5. Hold policy: Should hold lines carry to next month automatically or remain in current run until resolved?
  6. PTA validation timing: Validate PTA format only at request submission, or also before billing run generation?
  7. Enable failure handling: If EM auto-enable fails at approval time, should item become approval_error and retryable?
  8. Notification scope: For v1, is in-app status enough, or do you want basic email notifications included now?
  9. Finance edits: Can finance modify amount in CSV, or should amount be read-only and only status/reason editable?
  10. Access model details: Which exact rule defines "project admin" in this instance for submit permission checks?
  11. Retroactive EM disable: If a previously approved EM is later disabled, should open carry-forward lines be cancelled?
  12. Duplicate prevention: Should same project+EM+month line be hard-blocked from duplicate generation at DB/entity level?

6) Risks and Mitigations

Risk Impact Mitigation
Duplicate billing lines Overbilling Add uniqueness checks on project+module+month+year and idempotent run logic.
Unclear finance status semantics Bad carry-forward outcomes Lock status dictionary and import validation with reject report.
Auto-enable fails silently User thinks EM is active when it is not Persist enable result and expose explicit error state in queue UI.
PTA changes mid-cycle Confusion in billing ownership Snapshot PTA at line creation and display both current PTA and snapshot PTA in UI.
