RMA Charges Migration Plan

Move EM billing operations from R2P2 to REDCap External Module Manager with approval queue, PTA tracking, monthly billing export/import, and carry-forward logic.

Date: June 29, 2026, updated July 6, 2026 · revised July 10, 2026 (request flow redesigned: catalog/cart → survey → PI approval → auto-enable/Jira · per-PTA finance CSV · PTA debt ledger · som-prod v1 scope — see Section 9) | Scope: New REDCap-only workflow, EM deactivation (Section 7), historical R2P2 data migration (Section 8)

1) Agreed Decisions

Confirmed Implementation Baseline

  • Approval should auto-enable requested EM(s) on approve.
  • A request can include multiple EMs.
  • Billing cutoff is end-of-month day 28/29.
  • Rejected charges carry forward next month with the same amount.
  • Finance upload should support all line statuses.
  • Request submission should be limited to project admins.
  • PTA changes affect future runs only (not already-generated lines).
  • Reversed No migration of historical R2P2 data is required. — full historical migration of EM-related charges is now confirmed, see Section 8.
  • Superseded 7/10 Notification scope for v1 is in-app status only — no email notifications. — the PI approval step now uses a REDCap Alert email (survey link). All other status surfaces remain in-app only.
  • Superseded 7/10 Approval is per line item (one EM per project = one line); an approved line auto-enables immediately regardless of other lines' outcomes in the same request. — the super-user approval queue is replaced by a PI/Admin survey approval covering the whole request; per-EM divergence happens after approval (auto-enable flag vs. RSSD Jira ticket). See Sections 2 and 9.
  • Deactivation is self-service for project admins — no super-user approval needed, except for system auto-detected deactivations, which still route through the queue.

2) Target Workflow Revised July 10, 2026

Cart → Survey → PI Approval Model (replaces the earlier Sequential Queue Model — no super-user approval queue)

  1. Requester (project "Design" right, som-prod) opens the EM Catalog page in the project's EM menu, browses requestable EMs with monthly fees (catalog managed in the EM-records project, PID 16000), and adds one or more to a cart.
  2. Checkout: requester enters the PTA number (regex-validated). The module creates a record in the request-tracking REDCap project (header + one EM line per cart item, status pending) and redirects to that record's survey.
  3. On the survey, the requester looks up the PI / Admin approver (Stanford person-lookup EM) and submits.
  4. A REDCap Alert emails the PI the approval survey: one Approve/Reject decision for the whole request (PTA + all EMs), with a note.
  5. On approval (redcap_save_record hook): the request's PTA auto-creates/updates the project's PTA mapping; each EM with the auto-enable flag (PID 16000) is enabled immediately (failure → approval_error, retryable); the rest go into one RSSD Jira ticket per request (REST API) as awaiting_super_user.
  6. The super user works the Jira ticket and enables those EMs manually; nightly reconciliation flips their lines to enabled.
  7. Requester tracks statuses in-app on the catalog page and on REDCap's core EM manager page (module-injected fee/PTA/status annotations).
  8. Monthly billing run (Diagram 3) creates charge lines from enabled + fee-bearing EMs; Finance CSV loop and carry-forward as in Section 4.

4) Data/Reporting Shape Revised July 10, 2026

  • Request Header + EM Lines: now REDCap records in the request-tracking project (not entities): project, requester, PTA, approver; repeating EM line — module prefix, fee snapshot, auto-enable snapshot, line status, Jira key, source.
  • Billing Run (finance_billing_runs entity): month/year, status (draft → exported → finalized), totals, generated by/at, exported/imported at.
  • Billing Lines (finance_billing_lines entity): project, module, amount, snapshot PTA, status, status source (generation | csv_import | manual) + who/when, attempt number, prior-line link, charge-entity link.
  • Finance CSV: the editable file is one row per PTA (finance rejects at PTA level; import fans the status out to that PTA's pending lines) + a read-only per-line detail file.
  • Unmapped projects: generated lines get status = hold + "No PTA mapping" — never dropped; they carry forward until the project is mapped.
  • Views: run detail grouped PTA → project → EM; Outstanding Balances ledger keyed by PTA (open rejected/hold lines attributed to each project's current PTA) — the backcharge tool.
  • Manual overrides: super user can set any line/PTA-group status with a required, audited note — allowed even after finalize (closes settled backcharges).
  • Scope v1: som-prod charges only (external_modules_charges.instance = som-prod).

5) Decisions Decided

Formerly "Open Questions" — all items below are now resolved. Original question kept for context, decision follows.

July 10, 2026 Items #1, #2, #4, #8 are superseded by the redesigned request flow and the per-PTA finance CSV — see Section 9 for the current decisions. Item #10 still defines who may submit (Design right), now applied to the catalog/cart page.

  1. Approval granularity: Should super users approve per-request only, per-line only, or both?
    Decided Per-line. One line = one EM within one project. Each line is approved/denied independently, even when it arrived as part of a multi-EM request.
  2. Reject behavior: If one line in a multi-EM request is rejected, should approved lines still auto-enable immediately?
    Decided No dependency between sibling lines — every EM request/line is independent and won't affect the others. If one line in a multi-EM request is rejected, the rest are unaffected and still auto-enable on approval, same as if they'd been submitted separately.
  3. Cutoff timezone: Which timezone governs day 28/29 cutoff (server timezone, institution timezone, configurable)?
    Decided No system-enforced timezone gate. The cutoff is operational, not automated: it's whenever the super-user actually clicks "Generate Report" for that month (day 28/29 is guidance for when to click it, not a server-side check). See Diagram 3, which drops the automated cutoff gate accordingly.
  4. Finance import key: What unique line identifier will finance preserve and return in CSV (line ID, external key, both)?
    Decided Both — the CSV Contract in Workflow_Diagrams.html already exports both line_id and billing_run_id; no change needed.
  5. Hold policy: Should hold lines carry to next month automatically or remain in current run until resolved?
    Decided Rolls to next month automatically, same treatment as rejected. Section 4's status table and the Workflow_Diagrams.html status flow are both updated.
  6. PTA validation timing: Validate PTA format only at request submission, or also before billing run generation?
    Decided At request submission only. No re-validation at billing run time.
  7. Enable failure handling: If EM auto-enable fails at approval time, should item become approval_error and retryable?
    Decided Yes — item becomes approval_error and retryable, and the error is surfaced to admins (not just logged silently).
  8. Notification scope: For v1, is in-app status enough, or do you want basic email notifications included now?
    Decided In-app is enough for v1. No email notifications. Diagrams 1–3 updated to drop email steps in favor of in-app status.
  9. Finance edits: Can finance modify amount in CSV, or should amount be read-only and only status/reason editable?
    Decided No amount modifications by finance. Matches the existing CSV Contract (amount/fee columns are export-only; only status and finance_note are editable).
  10. Access model details: Which exact rule defines "project admin" in this instance for submit permission checks?
    Decided REDCap users with the project's "Design" user right. This already matches the existing classes/User.php::hasDesignRights() helper (design right or SUPER_USER) — no new permission model needed.
  11. Retroactive EM disable: If a previously approved EM is later disabled, should open carry-forward lines be cancelled?
    Decided Don't cancel anything retroactively. Instead, prevent the problem at the source: when a monthly invoice/billing run is generated, only create a line item for a project+EM if, at that moment, the project is in Production status and the EM is currently enabled. Already-generated lines are left alone and run their normal course. See decision #15 and Section 7 / Diagram 2 (now simplified — no cancel-vs-finish gate needed).
  12. Duplicate prevention: Should same project+EM+month line be hard-blocked from duplicate generation at DB/entity level?
    Decided Yes, at the report level: once a report is generated for a month, a super-user can't generate a second one for that same month. If the existing report hasn't been sent to finance yet (still draft), they can append/regenerate it in place instead of creating a duplicate. See Diagram 3's new duplicate-report gate.
  13. Deactivation approval: Does deactivation need super-user confirmation like activation does, or can a project admin self-service deactivate without approval?
    Decided No approval needed. A project admin can deactivate any EM they no longer need directly — self-service, immediate. (Contrast with enablement, which still requires approval.)
  14. Auto-detected deactivation: When the nightly reconciliation job finds an EM disabled outside the workflow, should it still route through the super-user queue, or auto-close silently with just a log entry?
    Decided Goes through the admin queue. Unlike self-service deactivation, an out-of-band disable wasn't initiated through the system at all, so it's surfaced for a super-user to acknowledge or flag.
  15. Deactivation timing vs. cutoff: If an EM is deactivated after the billing cutoff but before the run is generated, is the current month still billed in full, or excluded?
    Decided Excluded. Enforced by the same generation-time check as #11: no Production+enabled, no line item, regardless of how much of the month it was active.
  16. Re-enable after deactivation: Does re-enabling a previously deactivated EM go through the full request/approval flow again, or is there a lighter-weight reactivation path?
    Decided Full request/approval flow again (Diagram 1) — no shortcut, even though deactivation itself is now approval-free.

6) Risks and Mitigations

Risk Impact Mitigation
Duplicate billing lines Overbilling Add uniqueness checks on project+module+month+year and idempotent run logic.
Unclear finance status semantics Bad carry-forward outcomes Lock status dictionary and import validation with reject report.

7) EM Deactivation Workflow Decided

Companion to Section 2's enablement flow, but not symmetric with it: deactivation is self-service (decision #13) except when the system detects an out-of-band disable, which still needs admin eyes (decision #14). Full flow diagram: Workflow_Diagrams.html, Diagram 2 — EM Deactivation Request & Approval Flow.

Target Workflow

  1. Project admin opens the EM management page, selects one or more currently-enabled EMs, and deactivates them directly — no approval step. The EM is disabled in REDCap immediately (if not already) and the request/items are recorded as deactivated for audit.
  2. OR a nightly reconciliation cron finds an EM disabled directly in redcap_external_module_settings with no matching deactivation record, and auto-creates one (source = auto_detected, status = pending). This one does go to the super-user approval queue for acknowledgment.
  3. No explicit "exclude from billing" step is needed: the monthly billing-run generation logic (decision #11) already only creates a line item when the project is Production status and the EM is currently enabled, so a deactivated EM simply stops generating new lines on its own.
  4. Already-generated/open billing lines for that project+EM are left untouched and run their normal course (charged/rejected/etc.) — deactivation does not retroactively cancel them (decision #11).
  5. Re-enabling a previously deactivated EM always goes through the full enablement request/approval flow again (decision #16, Diagram 1) — there is no lightweight reactivation shortcut.

Data Shape Revised 7/10

Reuse em_enable_requests / em_enable_request_items entities. Deactivations are recorded on the request-tracking REDCap project's EM-line instrument (same store as enablement requests — the planned entities are not built): line status deactivated with who/when/reason, and a source field (manual | auto_detected). manual deactivations (via the module's Disable button injected into REDCap's core EM manager page) are recorded already-resolved; auto_detected ones (nightly reconciliation) are created pending and appear in the acknowledgment queue on the request-admin page.

Corresponding decisions are in Section 5, items 11 and 13–16, and Section 9.

8) Historical R2P2 Data Migration Decided

Reverses the "no migration required" decision in Section 1. Full historical migration of EM-related charges is confirmed. This section was rewritten after finding that R2P2 already has a dedicated REDCap-linking model — the mapping is more direct than originally assumed.

Source data (R2P2)

Reviewed backend/app/projects/sow/invoices/ and backend/app/projects/redcap/ in the R2P2 codebase. Relevant models:

  • REDCapEMCharges (app_redcapemcharges, in app/projects/redcap/em_charges/) — the key model for this migration. It's already a replica of this module's external_modules_charges shape: redcap_instance, pid, year, month, module_prefix, amount. Its primary key, redcap_em_charge_id, is the corresponding REDCap external_modules_charges entity ID (per your note) — not a local autoincrement. It FKs to ChargeItem.
  • ChargeItem — the underlying per-month charge: SOW, PTA (via Finance), amount, start_date. Also carries redcap_custom_charge_id / redcap_custom_project_id / redcap_custom_charge_instance — confirmed to target REDCap's separate custom_charges entity (table redcap_entity_custom_charges, defined by the custom_charges_v9.9.9 module), not external_modules_charges.
  • custom_charges (REDCap-side, custom_charges_v9.9.9 module) — fields: project_id, module_prefix (optional), is_recurring, amount, notes, status, rma_id (R2P2's RMA id). Because module_prefix is optional, this entity holds a mix of EM-related charges (module_prefix populated) and genuinely non-EM charges (e.g. Twilio fees, per that module's own description) — it is not exclusively "not related to EMs."
  • InvoiceItem — one row per SOW per invoice: pta_num, amount, status (Pending=1 / Charged=2 / Rejected=3).
  • SOW — must be types = 2 (REDCap Maintenance Agreement) and status IN (2, 6, 7) (approved/active) to count as an EM-related charge — confirmed by existing R2P2 queries in ProjectREDCap.get_redcap_project_with_approved_rma() / get_redcap_project_with_broken_rma_billing(), which join exactly this chain: REDCapEMCharges → ChargeItem → InvoiceItem → SOW → Finance.
  • Finance (via SOW.finance_id) — pta_charge_number is the PTA on file.

Target

Reuse external_modules_charges (decided). Extend it with a source field (live | migrated_r2p2) plus traceability fields (r2p2_charge_item_id, r2p2_invoice_item_id) so a re-run can detect already-migrated rows and skip them.

Decisions (Decision Checklist)

  1. Scope: Decided Full history — but only EM-related charges (SOW types = 2 / RMA, approved/active status). R2P2 has other, non-EM SOW charge types that must be excluded.
    Default applied "EM-related" is read broadly: it includes both (a) ChargeItem rows linked via REDCapEMCharges, and (b) ChargeItem rows linked via redcap_custom_charge_id where the target custom_charges row has module_prefix populated. Purely non-EM custom_charges rows (no module_prefix) stay out of scope. You didn't confirm this when asked — I went with the broader reading since it matches your original "full EM charges" framing. Say the word if you meant REDCapEMCharges-only.
  2. Target entity: Decided Reuse external_modules_charges (see Target above), not a new dedicated entity. Rows sourced from custom_charges (path b above) are normalized into the same external_modules_charges shape on import — module_prefix carries over directly, and there's no month/year on the source side, so it's derived from ChargeItem.start_date.
  3. Mapping key: Decided Two valid linkage paths, checked in order: (1) ChargeItem → REDCapEMCharges (primary — already carries pid/module_prefix/amount/month/year directly); (2) ChargeItem.redcap_custom_charge_id → a custom_charges row with module_prefix populated (fallback, per the scope default above). If neither path resolves — no REDCapEMCharges link, and no populated redcap_custom_charge_id/redcap_custom_project_id/redcap_custom_charge_instance — the row is unmappable: skip it and log an error rather than guessing at a match.
  4. PTA mapping: Decided Yes, 1:1 — R2P2's Finance.pta_charge_number (via SOW) maps directly onto pta_accounts.pta_number. The import creates any missing pta_accounts / project_pta_mapping records on the fly.
  5. Date range: Decided Full history, no cutoff date.
  6. Status mapping: Decided Direct 1:1 — R2P2 Pending→pending, Charged→charged, Rejected→rejected. REDCap's two newer statuses (waived, hold) have no R2P2 source and are simply never produced by this migration.
  7. Delivery mechanism: Decided One-time export/import — not a standing repeatable tool. Built once, run once, retired.
  8. Data access: Decided No direct R2P2 database access. Proposed mechanism A one-time R2P2-side export (management command or admin view) serializes the joined REDCapEMCharges ⋈ ChargeItem ⋈ InvoiceItem ⋈ SOW ⋈ Finance rows (filtered per scope, #1) to a JSON/CSV file. A one-time PHP import page in this module (e.g. pages/migrate_r2p2_charges.php + an ajax handler) reads that file and creates external_modules_charges entities per the mapping rules above. This mechanism is my proposal, not something you specified — please confirm before I build it.

Decision #8 in Section 1 now reads "Reversed" — full historical migration of EM-related charges is in scope.

9) July 10, 2026 Design Revision Decided

Decisions from the July 10 design session. Where these conflict with Sections 1–5, these win. Full implementation detail: EM_Billing_Implementation_Plan.html; updated diagrams: Workflow_Diagrams.html (v2.0).

Request flow (replaces the super-user approval queue)

  1. Catalog & cart: project-side EM Catalog page (EM menu, som-prod, Design right required); catalog and fees managed as records in the EM-records project (PID 16000), including a new per-EM auto_enable flag.
  2. Survey handoff: checkout validates the PTA (regex) and pre-creates a record in a dedicated request-tracking REDCap project (system setting em-request-project-id), then redirects to the record's survey — no data passed through the URL.
  3. Approver lookup: requester selects the PI/Admin on the survey via the Stanford person-lookup EM.
  4. Approval unit: the PI approves/rejects the whole request (one decision covering the PTA and all EMs) on a second survey instrument delivered by a REDCap Alert email.
  5. Post-approval processing: redcap_save_record hook — per EM: auto-enable when flagged (failure → approval_error, retryable); otherwise one RSSD Jira ticket per request via REST API, lines awaiting_super_user until reconciliation sees the manual enable.
  6. PTA sync: an approved request's PTA auto-creates/updates pta_accounts and the project's active project_pta_mapping — the main way billing mappings stay current.
  7. Store: requests/lines live as tracking-project records; the previously planned em_enable_requests / em_enable_request_items entities are not built.

Billing / invoice / debt

  1. Line-level storage, view-level grouping: finance_billing_lines (one per project+EM+month, PTA snapshotted) under finance_billing_runs; invoice view groups PTA → project → EM. The JSON-snapshot monthly_pta_reports implementation is replaced.
  2. Debt owner = PTA: the Outstanding Balances ledger is keyed by PTA (open rejected/hold lines attributed to each project's current PTA; original attempt PTA kept on the line for audit).
  3. Finance rejects per PTA: editable CSV is one row per PTA; import fans the status out to that PTA's still-pending lines (all-or-nothing validation; manually-resolved lines skipped and reported). A read-only per-line detail CSV accompanies it.
  4. Carry-forward: re-bills the project's current PTA, same amount, attempt+1, linked via carried_from_line_id; created regardless of current enablement (it is already-incurred debt).
  5. Unmapped projects: lines generated with status = hold + "No PTA mapping" (excluded from the finance summary file, flagged at export) so nothing is silently dropped.
  6. Manual overrides: allowed any time, required note, audited (status_source = manual, who/when) — used to close settled backcharges.
  7. Scope v1: som-prod only; multi-instance keys (instance+project_id) deferred.

Deactivation, core page, reconciliation

  1. Core EM manager page injection: per-EM fee / PTA / request-status annotations plus a module-owned Disable button (confirm dialog, required reason, immediate, audited). Re-enable = full new request.
  2. Reconciliation cron (nightly): out-of-band disables → auto_detected record into the acknowledgment queue; Jira-resolved manual enables → line flipped to enabled.
  3. Go-live baseline: one-time seeding of grandfathered tracking records for every currently-enabled billable EM, so reconciliation starts from a complete picture.

Security fix (found during review)

ajax/finance_report_action.php and ajax/finance_report_download.php are currently listed in no-auth-pages with no permission or token check — they must be removed from no-auth-pages and guarded super-user-only before release.
