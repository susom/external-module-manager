🏥 RMA Billing Migration

External Module Manager – Workflow & Approval Process Analysis

Project Overview

Migrate RMA (Recurring Maintenance Agreement) charges from R2P2 into REDCap's External Module Manager. This document presents three workflow options for managing EM enablement requests, approval processes, and monthly billing cycles.

Option 1: Sequential Queue-Based Approval ⭐ RECOMMENDED

Overview

Straightforward approval queue. Users submit requests → centralized admin review queue → one-at-a-time approval → auto-enable EM → charge next billing cycle.

┌─────────────────────────────────────────────────────────────────────────────────┐ │ SEQUENTIAL WORKFLOW │ └─────────────────────────────────────────────────────────────────────────────────┘ PROJECT ADMIN REDCAP SUPER USER REDCap/System │ │ │ ├─ Fill PTA │ │ ├─ Select EMs │ │ └─ Submit Request ────────────→ Queue page lists pending │ │ requests (draft status) │ │ │ ├─ Review PTA & EMs │ ├─ Check Project Health │ ├─ Add Notes (optional) │ └─ Click "Approve All" ───────→ EM auto-enables │ or "Reject" with reason │ Item status = approved │ │ Monthly billing includes │ │ from next cutoff date │ │ (day 28/29 of month) │ └─── User notified by email of approval/rejection

Key Steps

  1. Request Submission: Project admin → select EMs → enter/confirm PTA → submit → status = "pending"
  2. Approval Queue: One page lists all pending requests, grouped by project (or PTA)
  3. Admin Action: Click row → drill-down: view project info, PTA, EMs, notes → approve/reject
  4. Auto-Enable: On approval, system immediately enables EM in REDCap (via external API/setting)
  5. Billing Snapshot: At month-end cutoff (28/29), cron creates billing lines for all approved+enabled EMs
  6. Finance Export: Monthly billing page generates CSV, finance downloads and processes
  7. Finance Re-import: Finance uploads CSV with updated statuses (charged/rejected/waived/hold)
  8. Carry Forward: Any rejected line creates new billing line next month with attempt# + 1, linked to prior line

Roles & Permissions

  • Project Admin: Submit requests, view own request history
  • REDCap Super User: View all pending requests in central queue, approve/reject, add notes
  • Finance Team: Export monthly runs, re-upload with statuses
  • System: Auto-enable/disable EMs, auto-generate monthly runs and carry-forwards
Pros
  • Simple mental model: submit → queue → approve → done
  • Straightforward audit trail (one request row per approval event)
  • Fast deployment; minimal extra roles/gates
  • Finance team workload is flat (one export/import per month)
  • Clear responsibility: admins approve, system executes
  • Easy to track approval SLA (all pending, sorted by date)
  • Low complexity: 3–4 entity types, ~3 pages
Cons
  • No security/compliance review stage (if org needs it later)
  • Admins must review every request individually (scales with volume)
  • If PTA changes mid-billing-cycle, affects only future runs
  • No built-in SLA escalation (requires manual follow-up)
  • No "draft" save option for multi-step requests
  • Rejected requests don't auto-retry; user must resubmit
Option 2: Parallel Approval Gates (Security + Finance)

Overview

Multi-stage approval. Request enters IT/Security review in parallel with Admin approval. Both must sign off before EM is enabled. Adds compliance & governance layer but increases processing time.

┌─────────────────────────────────────────────────────────────────────────────────┐ │ PARALLEL GATES WORKFLOW │ └─────────────────────────────────────────────────────────────────────────────────┘ PROJECT ADMIN REDCAP ADMIN IT/SECURITY System │ │ │ │ ├─ Submit Request ────→ Status = pending │ │ │ (PTA, EMs) both queues │ │ │ │ │ │ │ ├─ Admin Queue ──┐ │ │ │ │ (review PTA) │ │ │ │ │ → Approve │ │ │ │ │ ├──→ If both approved: │ │ │ │ EM auto-enables │ │ │ │ Status = enabled │ │ ├──→ Monthly billing │ │ │ includes from │ │ │ next cutoff │ Status = admin_approved │ │ │ │ │ │ Security Queue ──┐ │ │ │ (scan EM code, │ │ │ │ check license) │ │ │ │ → Approve/Reject │ │ │ │ ├─→ If rejected: │ │ │ Status = sec_rejected │ Status = security_approved │ User notified │ │ │ │ └──── Auditor Trail ───→ Log both approvals │ └──── Both approval paths stored, SLA tracked per user/gate

Key Steps

  1. Request Submission: Project admin submits; request enters both queues (admin_pending, sec_pending)
  2. Dual Queue: Admin page shows requests pending admin approval; Security page shows requests pending security approval
  3. Admin Gate: Admin reviews PTA, budget, project status → approve/reject
  4. Security Gate: Security scans EM source code, checks licenses, compliance → approve/reject (or request more info)
  5. Dual Check: Auto-enable triggers only if both gates approve
  6. Rejection Path: If either rejects, entire request rejected; user notified with reason from both gates
  7. SLA Tracking: Each gate has SLA clock; if admin approves but security delays, visible in dashboard
  8. Billing & Carry-Forward: Same as Option 1

Roles & Permissions

  • Project Admin: Submit requests
  • REDCap Admin: Approve based on project health, PTA, budget
  • IT/Security Officer: Review EM code, licenses, compliance; approve/reject
  • Finance Team: Export/import billing (same as Option 1)
  • Finance Approval (optional): Finance team could be a 3rd gate if costs exceed threshold
Pros
  • Compliance-ready: security review baked in from day one
  • Reduces risk: two independent reviewers catch issues
  • SLA visibility: see where approvals are bottlenecked
  • Scalable to add 3rd gate (Finance, etc.) later
  • Better audit trail: separate sign-offs for governance
  • Parallel processing: admin & security review simultaneously (faster than sequential if well-staffed)
Cons
  • Slower time-to-enable: both gates must finish (can be ~1–2 weeks)
  • More complex: 5–6 entity types, 4+ pages, state machine logic
  • Higher overhead for simple low-risk requests (overkill for common EMs)
  • Requires dedicated Security resource; not feasible if org lacks it
  • Rejection from one gate kills whole request (no partial approval)
  • Request management more fragmented (two separate queues to monitor)
Option 3: Pre-Approval Self-Service (Admin Batch Review)

Overview

Users self-enable EMs immediately (with PTA on file); system auto-tracks as pending-approval. Admins batch-review weekly and retroactively approve/reject. Billing includes only approved items. Fastest user experience, but requires strong admin discipline.

┌─────────────────────────────────────────────────────────────────────────────────┐ │ PRE-APPROVAL / SELF-SERVICE WORKFLOW │ └─────────────────────────────────────────────────────────────────────────────────┘ PROJECT ADMIN System REDCAP ADMIN Finance │ │ │ │ ├─ Fill PTA on project │ │ │ │ (stored in project) │ │ │ │ │ │ │ ├─ Browse available EMs ─────→ Auto-check: PTA on file? │ │ │ │ If YES: allow self-enable │ │ │ │ If NO: show error, require │ │ │ │ PTA first │ │ │ │ │ │ ├─ Click "Enable EM [X]" ────→ IMMEDIATE: EM enables in │ │ │ for [Module Y] │ REDCap + creates tracking │ │ │ │ record (status=pending_approve) │ │ │ │ │ "Enabled but pending │ │ │ │ admin review" message │ │ │ │ shows on project │ │ │ │ │ │ │ │ │ ← Weekly batch admin review (e.g., Mondays) │ │ │ │ │ │ Pending Approvals Page │ │ │ │ ├─ All pending_approve │ │ │ │ │ items from past week │ │ │ │ ├─ Bulk actions: │ │ │ │ │ "Approve All", or │ │ │ │ │ "Reject [X,Y]" │ │ │ │ └─ Send notif: "Admin │ │ │ │ reviewed this week" │ │ │ │ │ │ │ │ Month-End Cutoff ─ Cron │ │ │ │ ├─ Build billing run │ │ │ │ │ (EMs where status= │ │ │ │ │ "approved") │ │ │ │ │ │ │ │ │ └─────────────────────────► Export CSV │ │ │ │ Download + │ │ │ │ Send to │ │ │ │ Finance ──→ Process │ │ │ │ │ │ │ Upload with │ │ │ statuses back

Key Steps

  1. PTA On-File Requirement: Project must have PTA stored before EM self-enable is available
  2. Self-Enable: Project admin checks available EMs → clicks "Enable" → EM immediately activates, but flagged as pending approval
  3. Async Approval: Admin reviews pending items on a schedule (weekly, or as needed), in bulk
  4. Batch Actions: "Approve All Pending" or select specific items to reject with reason
  5. Retroactive Reject: If admin rejects after user has already enabled, EM is disabled, user notified
  6. Billing Logic: Only items with status="approved" are included in monthly billing run
  7. Carry-Forward: Rejected items create new billing line next month (if still enabled and re-approved)

Roles & Permissions

  • Project Admin: Must set PTA first; can immediately enable EMs (pending approval)
  • REDCap Admin: Batch-review pending items weekly; approve/reject in bulk
  • Finance Team: Export/import monthly billing (same)
  • System: Auto-enable/disable, auto-flag for approval, cron for monthly runs
Pros
  • Fastest user experience: No wait; enable now, admin validates retroactively
  • Admin can batch-process (more efficient than one-by-one)
  • Reduces request backlog pressure (no queue congestion)
  • Billing is still clean (only approved items charged)
  • Simpler workflow for low-risk projects (pre-approved by PTA requirement)
  • Admin has more context: can see how EM is being used before approving
  • Scalable: even with large volume, admins review once/week
Cons
  • Out-of-control risk: EMs are live before approval (if admin rejects, user already used it)
  • Billing chaos if admin forgets to batch-review (pending items pile up)
  • No SLA enforcement; admin could review late/never
  • Rejections after the fact upset users (they've already enabled EM)
  • Audit trail is messier (EM was live before approval)
  • Requires strong admin discipline and weekly reminder process
  • If PTA later changes/expired, billing run may include stale PTA
  • Harder to track "why was this not approved?"

🎯 Recommendation: Start with Option 1 (Sequential Queue)

Reasoning:

  • Lowest risk: Simple approval gate before EM is enabled and billed.
  • Fastest to deploy: 3–4 pages, standard entity setup, straightforward state machine (pending → approved/rejected).
  • Clear audit trail: One request ID, one approval event, easy to track who approved what and when.
  • Operational clarity: Admin has one queue to monitor; can set SLA expectations (e.g., "review within 3 business days").
  • Flexible later: If organization later needs multi-gate approval (Option 2) or bulk batching (Option 3), can add those features without rearchitecting.
  • Finance-friendly: Monthly billing is straightforward: "include only approved items."

Migration Path: Deploy Option 1 for v1 (2–3 sprints). After 2–3 months of live operation, gather feedback from admins and finance team. If needed, migrate to Option 2 or add batch-review capability (Option 3 hybrid) in v2.

💡 Bonus: Hybrid Approach (Option 1 + Option 3 for Low-Risk)

Middle ground: Implement Option 1, but add a risk tier:

  • Tier 1 (High-risk): Full approval queue (Option 1). Examples: paid EMs, complex integrations, new vendors.
  • Tier 2 (Low-risk): Pre-approval self-enable (Option 3). Examples: standard utility EMs, already-approved vendors, <$100/month.

System auto-checks EM against risk profile; if low-risk, enable immediately; if high-risk, send to queue. Admin can override risk tier per project if needed.

Benefit: 80% of users get instant gratification (low-risk), while risky requests still get scrutinized.

⚙️ Key Implementation Decisions (All Options)

  • Monthly cutoff: Day 28 or 29 of each month at 23:59 (configurable); billing lines generated at cutoff.
  • Auto-enable mechanism: On approval, system calls REDCap API or updates DB to enable EM in production instance.
  • PTA storage: Plain string in project-level entity; can add validation regex later.
  • Billing lines: One line per project+EM+month; carry-forward: new line with prior_line_id + attempt# = 2.
  • CSV import: Finance updates status field (charged/rejected/waived/hold); system processes on re-upload.
  • Rejected line handling: If rejected, status = "rejected", rejection_reason stored; next month, new line created with attempt# = attempt# + 1.
  • Notifications: Email on request approval, rejection, and end-of-month billing export (can be built in v2).
  • Hard cutover date: TBD; migration script imports no data from R2P2 (users refer to R2P2 for historical months).
