📋 Diagram 1 — EM Enablement Request: Cart → Survey → PI Approval

Redesigned July 10, 2026 — replaces the super-user approval queue. A requester with the project's "Design" right (som-prod, v1) opens the EM Catalog page in the project's EM menu, adds fee-bearing EMs to a cart (catalog + fees + auto-enable flag come from the EM-records project, PID 16000), and checks out with a regex-validated PTA. The module pre-creates a record in the request-tracking REDCap project and redirects to its survey, where the requester picks the PI/Admin approver via the Stanford person-lookup EM. A REDCap Alert emails the PI an approval survey — one Approve/Reject decision for the whole request. On approval, the redcap_save_record hook syncs the PTA into the billing mapping, auto-enables flagged EMs (failure → approval_error, retryable), and opens one RSSD Jira ticket per request for the rest (awaiting_super_user until nightly reconciliation sees the manual enable). Re-enabling a deactivated EM (Diagram 2) comes back through this same flow with no shortcut.

🛑 Diagram 2 — EM Deactivation & Nightly Reconciliation

Revised July 10, 2026. Deactivation is self-service and immediate — via the module's own Disable button injected into REDCap's core EM manager page (each EM row is annotated with fee · PTA · request status). The confirm dialog requires a reason; the module disables the EM and records the deactivation on the tracking record (who · when · reason). No approval gate, no billing step: the monthly run only creates a line when the project is Production and the EM is enabled, so a deactivated EM stops generating new lines on its own — already-open lines run their normal course. The nightly reconciliation cron does two jobs: it files out-of-band disables as auto_detected records for super-user acknowledgment, and it flips awaiting_super_user lines to enabled once the Jira-ticketed manual enable actually happened. At go-live, a one-time seeding creates grandfathered tracking records for every currently enabled billable EM so reconciliation starts from a complete baseline. Re-enabling requires the full Diagram 1 flow again.

💰 Diagram 3 — Monthly Billing Run, Finance CSV Loop & Debt Ledger

Revised July 10, 2026. Generation is admin-triggered (day 28/29 is guidance, not a gate). One run per month: finalized/exported blocks regeneration, a draft regenerates in place. New lines come from that month's external_modules_charges (som-prod, fee-bearing); open rejected/hold lines from prior runs carry forward — same amount, attempt+1, billed to the project's current PTA. Projects without a PTA mapping get lines at hold ("No PTA mapping") under an Unmapped group — never dropped. Export produces two files: the editable summary CSV, one row per PTA (finance rejects at the PTA level) and a read-only per-line detail CSV. Import is all-or-nothing on validation, fans each PTA's status out to its still-pending lines (manually-resolved lines are skipped and reported), and finalizes the run. Open rejected/hold lines feed the Outstanding Balances ledger keyed by PTA — the backcharge tool; the super user can manually override any line or PTA group (required, audited note) at any time, including after finalize.

📄 CSV Contract — Two Files (revised July 10, 2026)

Finance receives two files. They edit and return only the Summary CSV — one row per PTA, because Finance charges/rejects whole PTAs. On import, each PTA row's status fans out to all of that PTA's still-pending lines in the run. The Detail CSV (one row per project+EM line) is a read-only reference and is never re-imported. Amounts are read-only everywhere (Migration Plan §5, decision #9).

🗄️ Entity & Status State Reference (revised July 10, 2026)

Request-tracking project — EM line status flow (REDCap records, not entities)

pending  → PI approves whole request →  approved
approved  →  enabled  (auto-enable flag set in PID 16000)
approved  →  awaiting_super_user  (RSSD Jira) →  enabled
approved  →  approval_error  (enable failed — surfaced, retryable)
pending  →  rejected  (PI rejects — new request to retry)
enabled  →  deactivated  (self-service or acknowledged auto-detect)

Deactivation sources

source = manual — module Disable button on REDCap's core EM manager page; recorded already-resolved as deactivated, no queue entry (decision #13)
source = auto_detected — nightly reconciliation finds an out-of-band disable: pending ack  →  deactivated  (super-user acknowledges, decision #14)
source = grandfathered — one-time go-live seeding of already-enabled billable EMs, created as enabled

finance_billing_lines status flow

pending  →  charged
pending  →  rejected  → carry forward next month (current PTA · attempt+1)
pending  →  waived  (no carry forward)
pending  →  hold  → carry forward next month (same as rejected, decision #5; also the auto-status for unmapped projects)
Any status may also be set manually by a super user (required note; status_source = manual; allowed post-finalize).

finance_billing_runs status flow

draft  →  exported  →  finalized
One run per month. Draft regenerates in place; exported/finalized blocks regeneration (decision #12).

  • finance_billing_lines — run_id, project, module, amount, snapshot PTA, status, status_source (generation | csv_import | manual) + who/when, attempt_number, carried_from_line_id, charge-entity link.
